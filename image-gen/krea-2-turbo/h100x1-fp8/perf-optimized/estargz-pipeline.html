How a streamable, optimized image variant gets built (and why cold starts dropped)

Krea-2-Turbo on Baseten, evidence from the cold-start branch (configs/cold-start/RESULTS.md). Three views: the build pipeline, the anatomy of a streamable layer, and what each stage does to wake-from-zero time.

1. The pipeline: from truss push to a streamed pull

truss push

Deployment config + code go to Baseten's builder.

BuildKit build

Emits the deployment image as gzip eStargz (compression=estargz, force-compression=true) so every layer, including inherited base layers, is seekable.

:…-estargz

Streamable format, naive layout: nothing useful sits before the landmark, so a wake still behaves like a full 19 GB pull (~4 min).

async, ~20-25 min later
Optimizer

Runs the container, traces which files boot actually touches, reorders them to the front, inserts .prefetch.landmark, re-pushes. Ours also shrank 19.05 → 17.08 GB.

:…-estargz-optimized

Deployment switches to this tag automatically. Wakes now stream: 5.1s measured pull.

Node runtime

Forked stargz-snapshotter FUSE-mounts layers: prefetches the prioritized region in one GET (120s budget), lazy-faults the rest in 64 MiB chunks via the node-local registry proxy. Untouched files are never downloaded.

2. Anatomy of one eStargz layer

The landmark file splits the layer. On-disk order inside the prioritized region is what the optimizer controls.
TOC
prioritized region
lazy region (never fetched unless touched)
Before the landmark: python bytecode + the exact .so files boot loads, in access order. Fetched eagerly as one HTTP GET; must complete inside the 120s prefetch budget (~8.4 GB at observed ~70 MB/s).
.prefetch.landmark marks the split.
After the landmark: everything else. On-demand, 64 MiB chunks, up to 16-wide. Dead weight here costs zero at startup, which is why image slimming and layout beat raw size.

4. Reproducing it by hand (for base images or beating the async lag)

# 1. Streamable FORMAT — buildx, force-compression re-encodes base layers too
docker buildx build --push --platform=linux/amd64 \
  --output type=registry,compression=estargz,oci-mediatypes=true,force-compression=true ...

# 2. Optimized LAYOUT — run + trace + reorder + landmark (stargz-snapshotter tooling)
ctr-remote image optimize --oci     # workload should exercise real boot/warmup

# 3. Verify — there is no per-deployment streaming metric; infer from pull-time vs size,
#    and check container start latency on a fresh node.
Qualifiers that travel with the numbers. (1) The optimized variant appears ~20-25 min after each deploy; wakes inside that window full-pull (~4-6 min). (2) Timings start at "compute acquired": GPU capacity acquisition on a tight cluster is additive and unmeasured here. (3) Weights times assume BDN has the 36 GB warm on-node (~13s truly cold). (4) Only gzip eStargz streams on Baseten (no zstdchunked); the default docker client silently produces plain gzip, which never streams.
